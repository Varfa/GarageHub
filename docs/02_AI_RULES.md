# Правила разработки проекта GarageHub

Версия: 1.0

---

# 1. Общие принципы

GarageHub разрабатывается как реальная коммерческая система управления СТО.

Главные цели проекта:

- чистая архитектура;
- читаемый код;
- простота сопровождения;
- возможность расширения без переписывания системы.

При принятии любого решения предпочтение отдаётся простоте и понятности.

---

# 2. Архитектура проекта

Используется Layered Architecture.

Структура проекта считается утверждённой.

Изменение структуры допускается только при наличии объективной необходимости.

Каждый слой отвечает только за свою область ответственности.

Handler
↓

Service
↓

Repository
↓

Database

---

# 3. Ответственность слоёв

Handler

- принимает HTTP-запросы;
- валидирует входные данные;
- вызывает Service;
- возвращает HTTP-ответ.

Handler НЕ содержит бизнес-логики.

---

Service

- содержит всю бизнес-логику;
- принимает решения;
- управляет процессами системы;
- вызывает Repository.

---

Repository

- работает только с PostgreSQL;
- содержит SQL-запросы;
- не содержит бизнес-логики.

---

Model

Содержит только структуры данных.

---

Validator

Содержит проверки входных данных.

---

Response

Отвечает за единый формат HTTP-ответов.

---

# 4. Правила написания кода

Каждая функция должна выполнять только одну задачу.

Не использовать огромные функции.

Предпочитать маленькие читаемые функции.

Избегать дублирования кода.

Следовать принципу KISS (Keep It Simple).

Следовать принципу DRY (Don't Repeat Yourself).

---

# 5. Работа с Git

Каждый законченный Sprint завершается:

- commit;
- обновлением документации (если требуется).

Commit должен иметь понятное описание.

Пример:

feat(users): add user repository

fix(router): health endpoint

refactor(service): repair validation

---

# 6. Работа с базой данных

Все изменения структуры БД выполняются через migrations.

Запрещается изменять структуру базы вручную.

Repository является единственным местом работы с SQL.

---

# 7. Работа с документацией

Документация является частью проекта.

При изменении архитектуры документация обновляется одновременно с кодом.

---

# 8. Правила разработки

Не писать код "на будущее".

Каждая новая функция появляется только тогда, когда она действительно необходима.

Не усложнять систему без необходимости.

---

# 9. Использование AI

AI используется как помощник архитектора и разработчика.

Любое решение AI должно быть понятно разработчику.

Запрещается копировать код без понимания его работы.

---

# 10. Главный принцип проекта

Код должен быть понятен самому себе через один год.

Если спустя год невозможно быстро понять написанный код — решение считается неудачным.

---

# Девиз проекта

Сначала архитектура.
Потом код.
Потом оптимизация.

Не наоборот.

Конфигурация приложения хранится в виде вложенных структур. Плоские структуры с десятками полей не используются.
Пакет полностью отвечает за свои данные. Внешний код не должен знать детали его реализации.
Перед написанием любой функции сначала проектируем её алгоритм простыми словами. Только после утверждения алгоритма пишем код.
go.mod и go.sum никогда не редактируются вручную без веской причины. Ими управляет Go.
